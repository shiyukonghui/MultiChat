# MultiChat 功能决策点

## 1. 后端框架选型：Axum

**决策日期**: 2026-05-26

**决策**: 选择 Axum 作为 Rust 后端 Web 框架。

**理由**:
- Axum 是 Tokio 生态的官方 Web 框架，与 Tokio 异步运行时深度集成
- 原生支持 SSE（Server-Sent Events），无需额外中间件
- 类型安全的路由和请求提取器，减少运行时错误
- 活跃的社区维护和良好的文档

**备选方案**:
- Actix-web: 生态成熟但 SSE 支持不如 Axum 原生
- Warp: 基于 Filter 的组合式 API，学习曲线较陡

---

## 2. LLM 网关选型：llmg-gateway

**决策日期**: 2026-05-26

**决策**: 使用 llmg-gateway (v0.3+) 作为统一的 LLM 调用网关。

**理由**:
- 内置 70+ Provider 支持，覆盖主流 LLM 服务商
- 统一的调用接口，屏蔽不同 Provider 的 API 差异
- 支持流式响应（streaming），满足实时推送需求

**备选方案**:
- 直接调用各 LLM API: 需要各自实现适配层，维护成本高
- langchain-ai-rust: 功能更丰富但引入复杂度，V1.0 暂不需要

---

## 3. 前端状态管理：React Hooks

**决策日期**: 2026-05-26

**决策**: 使用 React 内置的 useState + useReducer 进行状态管理，不引入 Redux。

**理由**:
- 应用状态结构相对简单，主要集中在聊天对话状态和模型状态
- useReducer 足以管理复杂的聊天状态机（发送中/流式更新/完成/错误）
- 避免引入额外依赖，降低学习成本和打包体积

**备选方案**:
- Redux Toolkit: 适合大规模应用，当前项目状态复杂度不需要
- Zustand: 轻量级状态管理，但 useReducer 已足够

---

## 4. SSE 连接管理策略

**决策日期**: 2026-05-26

**决策**: 使用浏览器原生 EventSource API 建立 SSE 连接，GET 请求通过查询参数传递消息和历史。

**理由**:
- EventSource 原生支持自动重连，减少手动实现复杂度
- 不需要引入第三方 SSE 客户端库
- 遵循需求文档中定义的接口规范（GET + 查询参数）

**注意**: 查询参数传递对话历史可能超出 URL 长度限制，后续大数据量场景可考虑升级为 POST + fetch + ReadableStream 方案。

---

## 5. 前端项目构建工具：Vite

**决策日期**: 2026-05-26

**决策**: 使用 Vite 作为 React + TypeScript 项目的构建工具。

**理由**:
- 极快的冷启动和热更新（HMR），开发体验优秀
- 原生支持 TypeScript 和 JSX，无需额外配置
- 内置开发代理（proxy），方便对接后端 API
- 是当前 React 社区的推荐工具

**备选方案**:
- Create React App (CRA): 已不再积极维护，启动速度慢
- Next.js: 服务端渲染能力在纯 SPA 项目中不需要，引入额外复杂度

---

## 6. 对话历史持久化：localStorage

**决策日期**: 2026-05-26

**决策**: V1.0 使用浏览器 localStorage 存储对话历史，不引入后端数据库。

**理由**:
- V1.0 聚焦核心对话功能，不需要用户认证和云端存储
- localStorage 实现简单，满足"页面刷新后保留历史"的需求
- 对话历史存储在客户端，无需额外的服务端状态管理

**后续计划**: V1.4 版本将支持用户登录和对话历史云端存储（参考需求文档演进路线）。

---

## 7. API Key 安全管理

**决策日期**: 2026-05-26

**决策**: API Key 仅通过环境变量注入，命名规范 `LLM_API_KEY_{PROVIDER}`，日志中只显示前 4 位 + 掩码。

**理由**:
- 环境变量是 12-Factor App 推荐的配置管理方式
- 避免 API Key 硬编码在代码或配置文件中
- 日志脱敏防止密钥泄露

---

## 8. 请求参数传递方式：GET + 查询参数

**决策日期**: 2026-05-26

**决策**: SSE 流式对话接口使用 GET 方法，通过查询参数传递 message 和 history。

**理由**:
- 遵循需求文档中明确定义的接口规范
- EventSource API 仅支持 GET 请求，与 SSE 协议天然匹配
- 简化前端实现

**风险**: URL 长度限制约 2000 字符，对话历史较长时可能超出。如遇此问题，后续可改用 POST + fetch API + ReadableStream 方案。
